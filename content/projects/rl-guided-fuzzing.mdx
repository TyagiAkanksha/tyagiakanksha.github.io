## Problem

A fuzzer looks for bugs by feeding a program a stream of mutated inputs and
watching what breaks. Classic fuzzers mutate blindly: they pick a mutation
and a place to apply it at random, so much of their budget goes on inputs
that exercise the same shallow paths. Our target was the control software of
a power generation system, whose inputs are configuration files full of
frequency and RPM settings. We wanted a fuzzer that learns which settings
are worth mutating, and how.

## Approach

We framed fuzzing as a Markov decision process and solved it with
reinforcement learning. I designed the core algorithm, which mutates several
input parameters in each round rather than one, and I built the parts that
let it learn.

- **The environment.** A Gym style environment whose state is 40 parameters
  read from the target's configuration files: 20 frequency settings and 20
  RPM settings, such as setpoints, offsets, limits and error ranges.
- **The actions.** A multi-discrete action space, so on every step the agent
  chooses both the mutation and the parameter it applies to. Traditional
  fuzzers apply mutations to parameters picked at random. Letting the agent
  pick the target is the new part, and it cuts down on wasted mutations.
- **The mutators.** The agent chooses from six mutators: flip one bit, flip
  several bits, replace a byte, erase a byte, insert a random byte, and
  shuffle the bytes.
- **The reward.** Each mutated input runs through the target, and the reward
  combines whether it crashed with how much of the code it covered. A crash
  counts far more than coverage (in my design notes the weights are 1000 and
  5), so the agent hunts for crashes first while still being pushed toward
  more coverage.
- **The agent.** A2C, short for Advantage Actor Critic. An actor network
  chooses the action, a critic network estimates how good the current state
  is, and the advantage, how much better an action turned out than the
  critic expected, steers each update. A2C learns from the steps it samples,
  so it needs no model of how the target program will respond.

## Architecture & Tech

A Python training loop couples the A2C agent to the fuzzing harness. On each
step the agent picks a mutation and a parameter, the harness applies it to
the configuration, runs the target, measures code coverage and checks for a
crash, and the reward goes back to the agent. The experiments compare the
learned policy with traditional fuzzing on coverage and on crashes found.

## Results & Impact

On the power generation control system, the fuzzer reached 70% code coverage
and found twice the crashes of traditional fuzzing. I am a coauthor of the
paper, "A Reinforcement Learning Approach to Multi-Parametric Input Mutation
for Fuzzing", which was published at IEEE CSR 2025.

## What I'd do next

I would run the fuzzer against a broader set of target programs, study
whether a policy trained on one family of targets transfers to another, and
package the learning layer so it can be attached to existing fuzzers.
