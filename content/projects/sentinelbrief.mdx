## Problem

A honeypot that faces the internet records attacker sessions all day, and
each one arrives as raw JSON. Most of it is routine scanning, and a small
part deserves a closer look. An analyst reading that stream by hand
either falls behind or stops looking. What they need is a short, ranked
queue where every entry explains itself.

## Approach

SentinelBrief sits between the honeypot and the analyst. It ingests real
SSH sessions, lets a model gather context through tool calls, and
publishes a verdict for each session with a severity, a category, a
confidence score, written reasoning, and a recommended action.

The human always decides. Nothing in the system blocks an address,
isolates a host, or answers an attacker. It only ranks and explains.

I also built it to be measured. An evaluation harness scores accuracy,
cost, and latency against a fixed set of real sessions, and it runs as a
gate in CI, so a prompt or model change that makes triage worse does not
ship. The results are kept on an append only record, including the runs
that came out worse than the ones before them.

## Architecture & Tech

A Cowrie SSH honeypot runs on its own host, isolated in a separate AWS
VPC. When a session ends, a small Python shipper posts it to the API with
an HMAC signature. If the API cannot be reached, the shipper keeps the
session in a spool on disk and retries, and a session that keeps failing
goes to a dead letter folder instead of being lost. The FastAPI service
verifies the signature, drops duplicates by fingerprint, stores the alert
in PostgreSQL, and returns right away.

All model work happens in background workers built on ARQ and Redis, so
ingestion never waits for a model response. No public request can trigger
a model call at all, and an import contract in CI keeps the model client
out of the API process. The worker runs a triage agent with five
enrichment tools: the commands typed in the session, information about
the targeted asset, geolocation and network owner, IP reputation, and the
alert history for the same source.

Attacker sessions are hostile input. Everything the attacker typed reaches
the model only inside clearly marked delimiters, and the tool loop stops
after six steps. The verdict is validated against a schema and retried
once if it does not parse, and every verdict records its models, tokens,
cost, and latency.

A fast model handles every alert first. When it reports a high severity or
a low confidence, the alert goes to a stronger model, which sees the same
evidence but not the first verdict, so it is not anchored by it. Every tool
call is stored as a reviewable trace.

Triage is idempotent. Jobs have deterministic IDs, the alert row is locked
while it is triaged, and retries are bounded. Integration tests on real
PostgreSQL and Redis crash and restart the worker and confirm that each
alert still gets exactly one verdict. CI also runs strict mypy and fails
the build if backend test coverage drops below 90%.

The dashboard is a public Next.js app with no login. New alerts arrive on
it live over Server-Sent Events, and if the stream drops it falls back to
polling every 30 seconds. Each alert page shows its recorded tool calls.
Every public read endpoint is rate limited per IP address, with the
counters kept in Redis.

The stack runs on AWS EC2 with Docker Compose behind Caddy, with images in
ECR, secrets in SSM Parameter Store, and IAM deny policies. PostgreSQL is
backed up to S3 every night, and a restore script brings a backup back.

## Results & Impact

- Between Sep 12 and Nov 21, 2026, the honeypot fed in 9,896 alerts. The
  platform triaged 6,561 of them at a mean cost of about $0.0017 per
  alert, and sent 24% to the stronger model.
- The first 32 live sessions came from 18 attacker IPs. All of them were
  triaged, exactly one was escalated, and the other 31 were rated at
  severity 1 or 2.
- The evaluation set holds 252 real honeypot sessions, seven of them
  tagged as possible prompt injection attempts. A stronger model
  labeled them, so the scores measure agreement with that model and not
  human ground truth, and I state that plainly next to the results. A
  nightly CI gate checks severity agreement, critical alert recall, and
  cost. On that set, triage averaged about $0.0012 per alert with a 1.1
  second median model latency.
- To prove the gate works, I ran it against a deliberately degraded
  prompt. Severity agreement fell from 1.00 to 0.04 and critical alert
  recall from 1.00 to 0.00, and the gate stopped the change before
  release.

The [live dashboard](https://sentinelbrief.tyagiakanksha.com/) is public
and read only. Open any alert to see the verdict, the reasoning, and the
full tool trace behind it.

## What I'd do next

I would label a subset of sessions by hand to calibrate the model
generated labels. I would also rebalance the evaluation set, because most
real sessions are low severity, and the rarer high severity cases are the
ones that matter most.
