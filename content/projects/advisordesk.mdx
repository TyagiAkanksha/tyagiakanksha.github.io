## Problem

Financial advisory firms produce a steady stream of written guidance, but
their clients cannot easily get answers from it. The guidance lives in
documents and portals, so a client with a question has to search through
them or wait for an advisor to reply. A generic chatbot does not solve
this either. In a regulated space, an answer that cannot be traced back to
the firm's own published guidance creates risk instead of value.

I built AdvisorDesk to show how I would solve this, as a working platform
for a fictional advisory firm that runs on sample content I wrote.

## Approach

I treated the firm's published content as the single source of truth and
built the platform around it.

- An admin CMS lets advisors create, edit, tag, and publish guidance.
  Publishing is what makes content available to the assistant. Drafts stay
  invisible to it.
- A public client portal includes a RAG assistant that answers questions
  from published content only. Every answer carries numbered citations
  that link back to the source articles. When nothing published covers
  the question, the assistant says so instead of guessing.
- An agentic content layer exposes the CMS operations as 14 MCP tools, so
  a content manager can search, draft, edit, tag, publish, and review
  content in plain language, either from an agent panel inside the CMS or
  from Claude. The agent never publishes unless the person explicitly asks
  it to.
- An evaluation loop measures how well answers are supported by their
  sources. It collects weak answers from negative feedback, refusals, near
  misses, and low confidence retrieval, turns proposed fixes into drafts,
  and refuses any fix that makes the evaluation worse.

## Architecture & Tech

Two Next.js App Router applications, the admin CMS and the client portal,
share one FastAPI backend built with Pydantic, SQLAlchemy, and Alembic. The
backend is a single application split into layered packages for services,
RAG, auth, MCP, and the agent, and import contracts checked in CI stop one
layer from reaching into another. TypeScript API types are generated
from the backend's OpenAPI spec, and CI fails when the spec or the
generated types drift, which catches frontend and backend mismatches
before they ship.

Content and embeddings live in PostgreSQL with pgvector on Supabase.
Publishing an article splits it into chunks of about 400 tokens along its
headings, embeds them with OpenAI, and writes the vectors in the same
transaction. A question is embedded the same way and matched against
published chunks with an HNSW index. The six closest chunks come back, and
anything below a similarity of 0.5 is dropped. OpenAI then writes the cited
answer, which streams to the browser over Server-Sent Events. Public chat
is rate limited per IP address and per session.

The CMS calls the 14 MCP tools in process, and a remote MCP server exposes
the same tools to Claude. To let Claude connect, I wrote my own OAuth 2.1
authorization server with PKCE, dynamic client registration, tokens that
are checked against their intended audience, and refresh token rotation
that detects a reused token. Only an allowlisted admin can reach the tools,
after Google sign in and a consent screen.

CI in GitHub Actions holds a 95% coverage floor on the backend, along with
strict mypy, ESLint, Vitest, and a dependency audit that blocks the build.
The suites hold over 1,200 backend tests and over 500 frontend tests.

The API and both frontends run as Docker containers on one AWS EC2 host
behind Caddy, which handles TLS. Images live in ECR, secrets live in SSM
Parameter Store, and the host has no SSH access.

## Results & Impact

- On an 80 question golden set, scored by an LLM judge over three
  recorded runs, a mean 93% of answerable questions were fully supported
  by their cited sources. The assistant refused every out of scope
  question correctly. The set mixes plainly answerable questions with
  near misses, off topic questions, and questions that need more than one
  source, and the judge is a stronger model than the one that answers.
- In production, the median time to first token is 733 ms and the p95 is
  1.27 seconds, measured over 24 chats. Each answer costs about $0.0013.
- The regression gate works. In one rehearsal I wrote a deliberately bad
  draft that raised the overall score, and the gate still blocked it,
  because two individual questions got worse.
- A probe runs against the live site every six hours. It asks a real
  question and checks that a cited answer streams back, so it tests the
  whole chat path and not only a health endpoint.

The [client portal](https://advisordesk.tyagiakanksha.com/) is public and
needs no login, including the
[assistant](https://advisordesk.tyagiakanksha.com/chat). The admin CMS is
open only to the allowlisted owner account, so I describe it here instead
of linking to it. The site holds no real client data. This project is also
the case study for my talk, Beyond RAG: Building an Evaluated,
Self-Improving Agentic AI System.

## What I'd do next

I would finish a larger round of human labels to calibrate the evaluation
judge, since the current agreement check rests on a small sample. I would
run the acceptance gate against a staging copy of the content, so a fix is
judged before it reaches the live site rather than after. I would also move
the in process rate limit and latency counters into Redis, so the API can
run more than one worker.
